
1. g=x на каталоге
Прочитать notes.txt Алиса сможет, если знает имя и у самого файла есть право r для неё. Выполнить ls не получится: будет Permission denied.
Каталог — это таблица соответствий «имя → inode».
r даёт право прочитать эту таблицу, то есть получить список имён.
x даёт право пройти через каталог и найти запись по заранее известному имени.
С одним x Алиса не может перечислить содержимое, но cat project/notes.txt сработает. Ядро найдёт запись по имени, а дальше проверит права самого файла. Раздел 6 — зеркальная ситуация: при r без x имена видны, но открыть ничего нельзя.

2. Группа копии
У копии будет группа alice. cp не переносит файл, а создаёт новый в /home/alice/. Группа нового файла назначается в момент создания, по умолчанию это основная группа процесса. Setgid влияет только на файлы, которые создаются внутри каталога с этим битом. У /home/alice такого бита нет, а бит на исходном каталоге здесь ни на что не влияет.
Есть нюанс: cp -p сохраняет группу. Алиса состоит в developers, поэтому с этим флагом копия получит developers.

3. nologin + одно правило sudo
nologin не отменяет того, что злоумышленник уже выполняет команды от webapp через уязвимость. Но две меры закрывают два разных направления.
nologin: учётная запись не служит точкой входа. Через ssh, su или консоль в неё не зайти, подбирать пароль бессмысленно. Когда уязвимость закроют, вернуться обычным логином будет нельзя.
Одно правило в sudoers: это потолок повышения привилегий. От root доступна ровно одна заранее заданная команда, и больше ничего.
В группе sudo правило %sudo ALL=(ALL:ALL) ALL позволило бы получить root через sudo -i. Единственным барьером остался бы пароль. Тогда взлом одного приложения означал бы взлом всего сервера: доступ к /etc/shadow, бэкдоры, данные других пользователей. В связке «nologin + правило» ущерб ограничен правами самого webapp и одной командой.
Оговорка: правило должно быть узким. В нём не должно быть * и программ, из которых можно выйти в шелл (vim, less, find).

4. 777 против 700
Самому webapp права 777 не дают ничего нового: первая триада и там и там rwx.
Ядро применяет только одну триаду — первую подходящую:
Если UID процесса совпадает с владельцем, берётся первая триада.
Иначе, если процесс состоит в группе файла, берётся вторая.
Во всех остальных случаях — третья.
Поэтому утверждение «опасен только из-за третьей триады» неверно. 777 открыл то, чего не было при 700:
Участникам developers (кроме владельца) вторая триада дала rwx вместо ---. Третья триада для них вообще не проверяется.
Всем остальным третья триада дала rwx.
В итоге править конфиг может любой пользователь системы, в том числе другой взломанный сервис. Он может подменить то, что читает webapp: пароли к БД, пути, адреса. Бит x на YAML-файле при этом просто лишний.
